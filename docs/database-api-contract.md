\# Database and API Agreement



\## Shared database rules



\- Database name: real\_estate\_portal\_new.

\- Each member uses their own local MySQL installation.

\- Everyone uses the same agreed schema scripts.

\- Record IDs are UUID strings generated by Java.

\- Java ID type: String.

\- MySQL ID type: CHAR(36).

\- JSON ID type: string.

\- SQL table and column names use snake\_case.

\- Java fields and JSON properties use camelCase.

\- Phone numbers are text, not numeric values.

\- Monetary values use BigDecimal in Java and DECIMAL(15,2)

&#x20; in MySQL, measured in LKR.

\- Dates use YYYY-MM-DD.

\- Appointment times use HH:mm:ss.

\- Passwords are stored as hashes, never plain text.

\- Real database credentials must not be committed.



\## 1 User and Access Management



Table: users



\- id: CHAR(36), primary key

\- username: VARCHAR(40), required, unique

\- password\_hash: VARCHAR(255), required

\- email: VARCHAR(254), required

\- phone: VARCHAR(20), required

\- role: VARCHAR(20), required



Initial roles: BUYER, SELLER, ADMIN.



Public registration permits BUYER and SELLER only.

Creating the first administrator requires a controlled

setup process, not public registration.



\### Account read and update rules



\- ADMIN may list all accounts and view account details.

\- Other signed-in users may view only their own account.

\- Account owners may update their username, email, phone

&#x20; and password.

\- Only ADMIN may change an account's role.

\- Public registration accepts BUYER or SELLER only.

\- ADMIN may create BUYER, SELLER or ADMIN accounts.

\- Account IDs cannot change.

\- Usernames must remain unique, ignoring letter case.

\- A duplicate username returns 409.

\- Account responses never include passwords or password hashes.



Role changes:

\- Block a role change while any properties, appointments,

&#x20; offers or reviews reference the account.

\- Return 409 when references prevent a role change.

\- The last ADMIN cannot be changed to another role.

\- Last-ADMIN checks and changes must be atomic.



Authentication:

\- Password changes invalidate the account's existing sessions.

\- Protected requests must check the account's current role.

\- A deleted account's old session must not grant access.





\## 2 Property Listing Management



Table: properties



\- id: CHAR(36), primary key

\- owner\_id: CHAR(36), required, references users.id

\- title: VARCHAR(150), required

\- description: TEXT, required

\- city: VARCHAR(100), required

\- address: VARCHAR(255), required

\- price: DECIMAL(15,2), required

\- property\_type: VARCHAR(20), required

\- status: VARCHAR(20), required



Property types: HOUSE, APARTMENT, LAND.

Statuses: AVAILABLE, UNAVAILABLE.



The owner must be a SELLER.

Price must be greater than zero.



\## 3 Moving Service Directory Management



Table: moving\_companies



\- id: CHAR(36), primary key

\- company\_name: VARCHAR(150), required

\- email: VARCHAR(254), required

\- phone: VARCHAR(20), required

\- service\_areas: VARCHAR(500), required

\- description: TEXT, required

\- availability: VARCHAR(20), required



Availability values: AVAILABLE, UNAVAILABLE.



This directory does not require property, appointment,

offer or review records.



Company information is entered directly.



\## 4 Viewing Appointment Management



Table: appointments



\- id: CHAR(36), primary key

\- buyer\_id: CHAR(36), required, references users.id

\- property\_id: CHAR(36), required, references properties.id

\- viewing\_date: DATE, required

\- viewing\_time: TIME, required

\- status: VARCHAR(20), required

\- notes: TEXT, optional



Statuses: PENDING, CONFIRMED, REJECTED, CANCELLED, COMPLETED.



The buyer must be a BUYER.

The referenced property must exist.

An appointment does not require an agent profile.



\### Appointment creation and update rules



\- Only a BUYER may create an appointment.

\- The backend obtains buyerId from the signed-in account.

\- A new appointment starts as PENDING.

\- New bookings require an AVAILABLE property.

\- Booking and rescheduling require a future date and time.

\- Dates and times use Asia/Colombo local time.

\- buyerId and propertyId cannot change after creation.



Booking BUYER:

\- May edit the date, time and notes while PENDING.

\- May cancel their own PENDING or CONFIRMED appointment.

\- Rescheduling a CONFIRMED appointment requires cancelling

&#x20; it and creating a new request.



Relevant property SELLER:

\- May change PENDING to CONFIRMED or REJECTED.

\- May change CONFIRMED to CANCELLED or COMPLETED.

\- May mark an appointment COMPLETED only after its

&#x20; scheduled date and time.



ADMIN:

\- May view all appointments.

\- May cancel PENDING or CONFIRMED appointments.

\- Does not confirm appointments on a seller's behalf.



Scheduling:

\- Only one CONFIRMED appointment is allowed for the same

&#x20; property at the same date and time.

\- Confirmation must check this rule atomically to prevent

&#x20; simultaneous conflicting confirmations.

\- Return 409 when the requested confirmed slot conflicts.

\- Multiple PENDING requests for a slot are permitted.

\- The initial system checks exact start times only;

&#x20; appointment durations are outside the initial scope.



REJECTED, CANCELLED and COMPLETED appointments cannot

be edited or moved back to an active status.



Appointment updates cannot change the property's fields.



\## 5 Offer Management



Table: offers



\- id: CHAR(36), primary key

\- buyer\_id: CHAR(36), required, references users.id

\- property\_id: CHAR(36), required, references properties.id

\- amount: DECIMAL(15,2), required

\- message: TEXT, optional

\- status: VARCHAR(20), required



Statuses: PENDING, ACCEPTED, REJECTED, WITHDRAWN.



The buyer must be a BUYER.

The referenced property must exist.

The amount must be greater than zero.



\### Offer creation and update rules



\- Only a BUYER may create an offer.

\- The backend obtains buyerId from the signed-in account.

\- New offers require an AVAILABLE property.

\- A new offer starts as PENDING.

\- The amount must be greater than zero.

\- buyerId and propertyId cannot change after creation.



Offering BUYER:

\- May edit amount and message while PENDING.

\- May change their own PENDING offer to WITHDRAWN.

\- Cannot accept or reject an offer.



Relevant property SELLER:

\- May change PENDING to ACCEPTED or REJECTED.

\- Cannot edit the buyer's amount or message.



ADMIN:

\- May view all offers.

\- Cannot accept or reject offers on a seller's behalf.

\- May delete eligible offers under the deletion rules.



ACCEPTED, REJECTED and WITHDRAWN offers cannot be edited

or reopened.



Updates must check the current status atomically so that

conflicting simultaneous changes cannot both succeed.

Return 409 for a change that conflicts with the current status.



In the initial scope, acceptance records the seller's decision.

It does not reserve or sell the property, prevent other offers,

or automatically change property availability.



\## 6 Review and Feedback Management



Table: reviews



\- id: CHAR(36), primary key

\- reviewer\_id: CHAR(36), required, references users.id

\- property\_id: CHAR(36), required, references properties.id

\- rating: INT, required

\- comment: TEXT, required



Ratings must be between 1 and 5.

The reviewer account and property must exist.



The initial scope is property reviews only.

There is no agent-review system in this six-member design.



A review's propertyId cannot change after creation.

BUYER and SELLER accounts may create reviews.

A seller cannot review their own property.

Multiple reviews by the same account are permitted in the initial scope.

\## Standard CRUD operations



GET /api/{module}

Read the records the caller is permitted to see.



GET /api/{module}/{id}

Read one permitted record.



POST /api/{module}

Create a record.



PUT /api/{module}/{id}

Update permitted fields of an existing record.



DELETE /api/{module}/{id}

Delete an eligible record.



The placeholder {module} represents the agreed module path.

Each module has its own controller.



\## API request fields



The backend generates id values.



Users:

\- Registration: username, password, email, phone, role.

\- ADMIN account creation: username, password, email,

&#x20; phone, role.

\- Profile update: username, email, phone.

\- Password and role changes are separate permitted actions.

\- Never accept passwordHash from the frontend.



Properties:

\- Create: title, description, city, address, price,

&#x20; propertyType, status.

\- Update: the same editable fields.

\- The backend derives ownerId from the signed-in SELLER.

\- ownerId cannot change after creation.

\- ADMIN may edit existing listings but cannot create

&#x20; listings on behalf of a seller in the initial scope.



Moving companies:

\- Create and update: companyName, email, phone,

&#x20; serviceAreas, description, availability.



Appointments:

\- Create: propertyId, viewingDate, viewingTime, notes.

\- Reschedule while PENDING: viewingDate, viewingTime, notes.

\- Status change: status.

\- The backend derives buyerId and initial PENDING status.



Offers:

\- Create: propertyId, amount, message.

\- Revise while PENDING: amount, message.

\- Status change: status.

\- The backend derives buyerId and initial PENDING status.



Reviews:

\- Create: propertyId, rating, comment.

\- Update: rating, comment.

\- The backend derives reviewerId.

\- propertyId cannot change after creation.



Required text fields must not be blank.

Text must fit the documented database column lengths.

Optional notes and message may be omitted or null.

Reject invalid role, status and property-type values.

Reject attempts to change server-controlled identity fields.



\## Update endpoint conventions



PUT /api/{module}/{id}

Updates the module's editable content fields.

Send all fields required for that content update.



PATCH /api/appointments/{id}/status

Body: {"status": "CONFIRMED"}



PATCH /api/offers/{id}/status

Body: {"status": "ACCEPTED"}



PUT /api/users/{id}/password

Body: {"currentPassword": "...", "newPassword": "..."}



PUT /api/users/{id}/role

Body: {"role": "SELLER"}



Password changes are performed by the account owner and

require the correct current password.

ADMIN password resets are outside the initial scope.



Role changes require ADMIN permission.

Appointment and offer content updates must not change status.

Property status and moving-company availability may change

through their normal content update endpoints.

Appointment and offer status changes follow their module rules.



Successful content and status updates return 200 with the

updated record.

A successful password change returns 204 and requires login again.



\## Authentication endpoints



POST /api/auth/register

POST /api/auth/login

POST /api/auth/logout

GET /api/auth/me



Registration delegates to the same user creation service

instead of duplicating account validation.



\### Shared session and CSRF conventions



Member 1 owns shared authentication. All modules use it.



GET /api/auth/me:

\- Available before and after login; creates an anonymous session if needed.

\- Returns 200: {"user": null, "csrfToken": "..."} before login.

\- After login, user contains id, username, email, phone and role.

\- Never includes passwords or hashes. Set Cache-Control: no-store.



POST /api/auth/register:

\- Accepts username, password, email, phone and BUYER or SELLER role.

\- Returns 201 with public account fields; does not automatically log in.



POST /api/auth/login:

\- Accepts username and password.

\- Replaces the session and CSRF token on success.

\- Returns 200 with user and csrfToken, using the /me response shape.

\- Incorrect credentials return 401 with a generic message.



POST /api/auth/logout:

\- Invalidates the current session and returns 204.

\- Frontend clears its user and CSRF token.



Frontend:

\- Use relative /api URLs through the shared Vite proxy.

\- Include cookies using credentials: "include".

\- Fetch /api/auth/me before the first state-changing request.

\- Send X-CSRF-TOKEN on POST, PUT, PATCH and DELETE, including login

&#x20; and registration. Use the newly returned token after login.

\- After logout, fetch /api/auth/me before registering or logging in again.

\- Keep the CSRF token in memory, never in a URL.



Backend:

\- Missing or invalid CSRF tokens return 403.

\- Protected requests require authentication and current permissions.

\- Check current role and ownership; never trust client-supplied actor IDs.

\- Cookies use HttpOnly and SameSite=Lax; production HTTPS uses Secure.

\- Password changes invalidate every existing session for that account.

&#x20; Member 1 must provide account-wide session invalidation.

\- Other members use the shared current-user helper; they do not implement

&#x20; separate login systems or access another module's tables directly.



These are implementation requirements, not already implemented features.



\## Requests and responses



\- Exchange application data as JSON.

\- Use camelCase JSON names, such as ownerId and propertyId.

\- Return an object for one record.

\- Return an array for the initial list endpoint.

\- Use uppercase role and status values as documented.

\- Represent monetary amounts as decimal strings in JSON,

&#x20; for example "12500000.00".

\- Never return passwordHash in account responses.

\- Registration accepts password, not passwordHash.

\- IDs identify records; callers cannot choose another actor's

&#x20; identity by supplying buyerId or reviewerId.



\## HTTP status codes



200: successful read or update

201: record created

204: deleted successfully, with no response body

400: invalid input

401: authentication required or login failed

403: caller lacks permission

404: record not found

409: duplicate or conflicting operation

500: unexpected server error



\## Error response



Use this shared shape:



{

&#x20; "code": "VALIDATION\_ERROR",

&#x20; "message": "Explain what the caller needs to correct"

}



Do not return database passwords, SQL internals or stack traces.







\## Initial permission rules



Users:

\- A person may register an ordinary account.

\- Account owners manage permitted own-profile fields.

\- Only authorized administrators manage account roles.

\- Users cannot promote themselves.



Properties:

\- Anyone may browse available listings.

\- Sellers create listings for themselves.

\- Owners manage their listings.

\- Administrators may view and edit all listings and delete

&#x20; eligible listings.

\- Unavailable listings are visible only to their owner or ADMIN.

Moving companies:

\- Anyone may browse the directory.

\- Administrators manage directory entries.



Appointments:

\- Buyers create bookings for themselves.

\- Buyers see their own appointments.

\- Property owners see requests for their properties.

\- Sellers confirm or reject requests for their properties.

\- Owners and administrators have only explicitly permitted

&#x20; update and deletion actions.



Offers:

\- Buyers submit and see their own offers.

\- Sellers see offers for their properties.

\- Only the relevant seller may accept or reject an offer.

\- Buyers may revise or withdraw eligible pending offers.



Reviews:

\- Anyone may read property reviews.

\- Authenticated ordinary users may create reviews.

\- Authors edit their own reviews.

\- Authors or authorized administrators may delete reviews.



Every module enforces its permissions in the backend.

Frontend button visibility is not sufficient security.



\## Deletion rules



General:

\- DELETE permanently removes an eligible record.

\- The backend checks permissions and eligibility.

\- Successful deletion returns 204 with no response body.

\- A missing record returns 404 to an authorized caller.

\- An authenticated caller without permission receives 403.

\- A permitted deletion blocked by references or record

&#x20; status returns 409.

\- Foreign keys use restricted deletion.

\- Do not cascade-delete another module's records.



Users:

\- Only ADMIN may delete accounts.

\- The account must have no properties, appointments,

&#x20; offers or reviews referencing it.

\- ADMIN cannot delete their own signed-in account.

\- The last ADMIN account cannot be deleted or changed

&#x20; to another role.



Properties:

\- The owning SELLER or ADMIN may delete a property.

\- Deletion is blocked while appointments, offers or

&#x20; reviews reference the property.



Moving companies:

\- ADMIN may delete a moving company entry.



Appointments:

\- The booking BUYER or ADMIN may delete a PENDING

&#x20; appointment.

\- CONFIRMED, REJECTED, CANCELLED and COMPLETED

&#x20; appointments are retained.

\- Cancellation changes status; it does not delete a record.



Offers:

\- The offering BUYER or ADMIN may delete a PENDING offer.

\- ACCEPTED, REJECTED and WITHDRAWN offers are retained.

\- Withdrawal changes status; it does not delete a record.



Reviews:

\- The author or ADMIN may delete a review.



The frontend asks for confirmation before sending DELETE.

The backend enforces these rules even if a caller bypasses

the frontend.

\## Shared validation and response details



\- JSON request bodies use Content-Type: application/json.

\- IDs are generated server-side on creation; immutable afterwards.

\- Trim surrounding whitespace from ordinary text, but never alter passwords.

\- Password length is 8 to 128 characters. Hash using a maintained password

&#x20; encoder with a random salt; Member 1 owns its shared configuration.

\- Email must have valid basic email syntax; phone remains text.

\- Money must be positive, fit DECIMAL(15,2), and have at most two decimal

&#x20; places. Reject excess decimal places rather than silently rounding.

\- Use an explicit case-insensitive unique username constraint in MySQL.

\- Enforce primary keys, NOT NULL, foreign keys and supported-value/range

&#x20; constraints in SQL as well as backend validation where applicable.

\- Each response record uses the camelCase equivalents of its documented

&#x20; table columns; users omit passwordHash. Dates/times follow shared formats.

\- POST returns 201 with the created record. GET lists return arrays, including

&#x20; an empty array when no permitted records match. DELETE returns no body.

\- A caller attempting an operation on another person's existing private

&#x20; record receives 403. A missing record returns 404. Unauthenticated

&#x20; protected requests return 401 once CSRF validation passes.

\- Invalid input returns 400; invalid current password returns 400.

\- Checks for references, state transitions and deletion run transactionally;

&#x20; foreign-key conflicts return 409, not raw database errors.

\- Retrying the current appointment or offer status is a no-op returning 200;

&#x20; terminal-state content edits and other forbidden transitions return 409.

\- Confirmation requires a future appointment time and an AVAILABLE property.

\- Setting a property UNAVAILABLE does not automatically cancel existing

&#x20; appointments or offers. Owners manage those records explicitly.



\## Listing and search conventions



\- GET /api/properties supports optional q and city query parameters.

\- q matches title or description; city matches the city, ignoring letter case.

\- Apply filters together and always enforce listing visibility first.

\- Unfiltered module list endpoints return all records the caller may see.

\- Pagination is outside version 1. Order list responses by id ascending

&#x20; for a deterministic initial implementation.

\- Private appointment and offer lists include the buyer's own records,

&#x20; the seller's relevant property records, or all records for ADMIN.

\- Public moving-company lists include both availability values.

\- Public review responses contain reviewerId, not private account details.
